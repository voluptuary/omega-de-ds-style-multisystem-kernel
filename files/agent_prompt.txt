## 7. Audit Methodology and Technical Standards

Conduct a systematic audit based on the actual architecture of this repository.

First, establish the repository's identity, supported systems, implementation language, architecture, build process, testing infrastructure, and stated project goals. Do not assume the target hardware or emulate features that are not part of the project.

Then develop a subsystem inventory and prioritize work according to correctness risk, impact, dependency relationships, and existing evidence.

Where relevant, investigate:

### Core execution and CPU
- Instruction decoding and execution.
- Addressing modes and arithmetic flags.
- Registers, stack behavior, and program counter updates.
- Interrupts, exceptions, reset behavior, and execution boundaries.
- Instruction and machine-cycle timing.
- Memory access ordering and side effects.
- Undefined behavior, integer overflow, and invalid states.

### Memory and bus architecture
- Address maps and access permissions.
- RAM, ROM, banking, mirroring, and open-bus behavior.
- Memory-mapped hardware registers.
- DMA, arbitration, and timing interactions.
- Read/write side effects and bus contention where applicable.

### Video and graphics
- Frame and scanline timing.
- Pixel or dot timing when required for the target system.
- Rendering pipelines, tile and sprite evaluation.
- Palette behavior, priority rules, scrolling, and clipping.
- VBlank, HBlank, status flags, and rendering-related interrupts.
- Mid-frame register changes and timing-sensitive effects where applicable.

### Audio
- Channel behavior, timers, envelopes, sweep, and length counters.
- Frame sequencing and interrupts.
- Sampling rates, resampling, synchronization, and buffering.
- Determinism, clipping, and audio/video synchronization.

### Cartridges and peripherals
- ROM parsing and format validation.
- Mapper or banking behavior.
- Cartridge RAM, save data, and persistence.
- Controllers, input timing, and peripheral protocols.
- Unsupported formats and malformed-input handling.

### System integration
- Reset and initialization.
- Main-loop scheduling and subsystem synchronization.
- Save states and deterministic restoration.
- File I/O and ROM loading.
- Error handling, diagnostics, and recovery.
- Performance, memory usage, portability, and maintainability.

These are investigation categories, not assumptions that every subsystem exists in this project. Adapt the audit to the actual hardware and repository.

## 8. Evidence-Driven Correctness

Do not rely solely on code inspection, comments, previous agent conclusions, or intuition.

Where appropriate, triangulate implementation behavior using:

- Official hardware manuals and technical documentation.
- Well-established community documentation and hardware research.
- Trusted reference emulator implementations.
- Existing conformance tests and test ROMs.
- Unit tests, integration tests, property-based tests, and fuzz testing.
- Differential testing against a reference implementation.
- Cycle-accurate traces, register snapshots, memory traces, and timing measurements.
- Reproducible minimal test cases.
- Historical hardware behavior and documented compatibility requirements.

Distinguish documented hardware behavior from common emulator conventions, implementation assumptions, and uncertain reverse-engineered behavior.

When using a reference emulator, do not automatically assume that it is correct in every respect. Understand what behavior is being compared and whether the reference is appropriate for the target hardware revision.

Whenever feasible, create automated regression tests for verified defects.

A passing test suite is evidence, not proof that an emulator is correct. Identify important coverage gaps and explain their significance.

## 9. Finding Prioritization

Classify findings using a consistent severity scheme:

- **Critical:** fundamental execution failures, severe data corruption, security vulnerabilities, or failures that make a major supported system unusable.
- **High:** significant hardware inaccuracies, widespread compatibility failures, major subsystem defects, or severe reliability issues.
- **Medium:** meaningful inaccuracies, limited compatibility defects, or maintainability problems that create a credible risk of future failures.
- **Low:** minor correctness issues, localized edge cases, diagnostics, documentation gaps, or nonessential improvements.
- **Informational:** observations, technical debt, design tradeoffs, and recommendations without a demonstrated defect.

Use engineering judgment. Do not inflate severity to make the audit appear more productive.

Prioritize fixes based on evidence, user impact, regression risk, dependencies, and the ability to validate the outcome.

Avoid speculative rewrites when a narrow, well-tested fix is more appropriate.

1. Reproduce it or establish the strongest feasible evidence.
2. Determine its root cause.
3. Assess its scope and dependencies.

5. Add a regression test whenever feasible.
6. Implement the fix.
7. Run focused tests.
8. Run broader relevant tests, builds, and static checks.
9. Inspect the final diff for unrelated changes, regressions, accidental file removal, and style violations.
10. Update both audit documents with the result and remaining risks.

Do not make speculative changes merely to demonstrate activity.

Do not silently change intended hardware behavior to match a reference emulator when authoritative evidence contradicts that reference.

Preserve existing user changes. Before modifying files or performing Git operations, inspect the working tree and determine which changes belong to the ongoing audit and which may belong to someone else.

Never discard unrelated changes simply to obtain a clean working tree.

Use clear, descriptive commit messages. Group logically related, validated changes into appropriately scoped commits.

Publish a release only when warranted by the project's release criteria and when the changes have passed the required validation. Follow existing tagging, packaging, signing, and release procedures.

A release is not a substitute for a completed audit report.
